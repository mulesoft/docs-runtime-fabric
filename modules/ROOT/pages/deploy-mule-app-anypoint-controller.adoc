= Deploying and Managing Mule Applications Using Anypoint Controller for Kubernetes

Anypoint Controller is a Kubernetes operator that enables you to deploy and manage Mule applications on Runtime Fabric using GitOps workflows and Custom Resources (CR).

Key Benefits:

* Define application configurations declaratively in version control and let the controller automatically reconcile them with Anypoint Platform and your cluster.
* Use standard Kubernetes tools and practices to deploy Mule applications, including `kubectl`, Helm, and custom resources.
* Leverage Kubernetes features such as external secret managers, volume mounts, and RBAC policies to meet enterprise security requirements.

This guide shows you how to:

* Install and configure Anypoint Controller in your Runtime Fabric cluster.
* Deploy Mule applications using declarative MuleApplication Custom Resources.
* Monitor application status using Kubernetes-native status conditions.
* Update, delete, and manage application lifecycles with standard Kubernetes commands.
* Integrate with CI/CD and GitOps tools like ArgoCD, FluxCD, and Terraform.
* Configure Kubernetes-specific settings including volumes, secrets, and node affinity.
* Troubleshoot common deployment and configuration issues.

== Scope and Limitations

[NOTE]
This feature is currently in Limited General Availability (Limited GA). To enable Anypoint Controller for your organization, contact MuleSoft Support.

Supported features:

* Runtime Fabric Mule application deployments
* Mule runtime engine (Mule) versions 4.6 and higher
* Helm based Runtime Fabric installation or upgrade

Not supported features:

* CloudHub 2.0 Mule application deployments
* Scheduler-based Mule applications
* API proxy deployments
* `rtfctl` based Runtime Fabric installation or upgrade

[IMPORTANT]
Backup and restore functionality (during Limited GA phase) is not supported. Plan your recovery strategy accordingly, leveraging your Git repository as the source of truth for application configurations.

=== Installation Method

To use Anypoint Controller, you must:

* Have an existing Runtime Fabric installation using Helm, or
* Install or upgrade Runtime Fabric using Helm (see xref:install-helm.adoc[Install Runtime Fabric Using Helm]) or xref:upgrade-helm.adoc[Upgrade Runtime Fabric Using Helm]

=== Management Constraints

Understanding the management model is critical before deploying and managing applications with Anypoint Controller:

* Applications created via Mule Application Custom Resources can only be managed through the Custom Resource itself.
* All configuration changes must be applied by updating the Custom Resource YAML and applying it to the cluster.
* The Anypoint Platform Runtime Manager UI displays these applications in read-only mode.
* Attempts to modify or delete these applications via Anypoint Platform APIs result in an error.
* The Git repository remains the single source of truth for application configuration.

=== Configure Anypoint Controller in Helm Chart

To enable Anypoint Controller during Runtime Fabric installation or upgrade, in the Helm chart, configure these settings:

* `global.crds.install = true`
* `global.crds.anypointController.enabled = true`

==== For New Runtime Fabric Installations

. In your `values.yaml` file, add this configuration:

[source,yaml]
----
global:
  crds:
    install: true
    anypointController:
      enabled: true
----
[start=2]
. Install the Runtime Fabric agent:

[source,bash]
----
helm install rtf-agent <chart-repo>/rtf-agent \
  -f values.yaml \
  -n <rtf-namespace>
----

==== For Upgrading Existing Runtime Fabric Installations

. Update your `values.yaml` file with the same configuration as previously mentioned:

[source,yaml]
----
global:
  crds:
    install: true
    anypointController:
      enabled: true
----
[start=2]
. Upgrade the Runtime Fabric agent:

[source,bash]
----
helm upgrade rtf-agent <chart-repo>/rtf-agent \
  -f values.yaml \
  -n <rtf-namespace>
----

This configuration performs these actions:

* Installs the Mule Application Custom Resource Definition (CRD) in your cluster
* Enables the Anypoint Controller component within the Runtime Fabric agent
* Grants the Runtime Fabric agent necessary permissions to manage MuleApplication resources

=== Define MuleApplication Custom Resource

Use the Custom Resource Definition (CRD) to define and manage Mule application configurations similar to any Kubernetes resources through Kubernetes APIs. Anypoint Controller watches the Mule Application Custom Resource (MuleApplication CR) state and matches it against the desired configured state.

After installing the CRD, define your Mule application as a Custom Resource by creating a YAML manifest file on your local machine or in your Git repository. 

This file specifies deployment configurations such as CPU and memory resources, replica count, runtime version, application artifact details, properties, volume mounts for secrets and configuration files, and Kubernetes-specific settings. 

You apply this file to your Kubernetes cluster using `kubectl apply -f <filename>.yaml`, and Anypoint Controller deploys the application based on the specifications.

For a complete reference of all available MuleApplicationCR fields and configuration options, see xref:deploy-mule-app-anypoint-controller.adoc#understanding-custom-resource-definitions[Understanding Custom Resource Definitions].

==== Basic MuleApplication Structure YAML File

[source,yaml]
----
apiVersion: rtf.mulesoft.com/v1
kind: MuleApplication
metadata:
  name: my-hello-world-app
  namespace: my-apps
spec:
  target: my-rtf-target
  businessGroup: MyOrg
  environment: Production
  runtimeVersion: "4.8.0:2e-java8"
  application:
    group: my-org
    artifactId: hello-world
    version: "1.0.0"
    packaging: jar
  replicas: 2
  resources:
    requests:
      cpu: 500m
      memory: 1Gi
----

=== Configure Volumes and Volume Mounts

Anypoint Controller supports standard Kubernetes volume types, enabling you to mount files, secrets, and persistent storage into your Mule application containers.

Use the `volumes` and `volumeMounts` fields to securely provide sensitive data (credentials, API keys, certificates), configuration files, and persistent storage to your application:

* `volumes` +
Defines the storage volumes available to the application, such as Kubernetes Secrets, ConfigMaps, persistent volumes, or external secret stores.
* `volumeMounts` +
Specifies where to mount the volumes inside the application container and makes the data accessible at the specified file path.

When you specify `volumes` and `volumeMounts` in the MuleApplication CR:

. The controller includes these specifications in the Deployment resource.
. Kubernetes mounts the volumes into the Mule application container at the specified paths.
. Your Mule application can access the files at runtime.

[NOTE]
Volumes specified in the MuleApplication CR are mounted to the main Mule application container, not to sidecar containers.

==== Example: Mount Secrets from Kubernetes Secrets

Use Kubernetes native Secrets to store secret data on the Kubernetes cluster and mount them into your Mule application.

.1 Create a Secret in your Kubernetes cluster:

[source,bash]
----
kubectl create secret generic my-database-secret \
  --from-literal=db.username=admin \
  --from-literal=db.password=secret123 \
  -n my-apps
----
[start=2]
Mount it in your MuleApplication CR:

[source,yaml]
----
spec:
  volumes:
    - name: database-secret
      secret:
        secretName: my-database-secret
  volumeMounts:
    - name: database-secret
      mountPath: /mnt/secrets
      readOnly: true
----

The secret files are now accessible at:

* `/mnt/secrets/db.username`
* `/mnt/secrets/db.password`

==== Example: Mount a TLS Keystore from a Secret

. Create a Secret containing your keystore:
+
[source,bash]
----
kubectl create secret generic java-keystore \
  --from-file=keystore.jks=./path/to/keystore.jks \
  --from-literal=keystore.password=changeit \
  -n my-apps
----

. Mount it in your MuleApplication CR:
+
[source,yaml]
----
spec:
  volumes:
    - name: tls-keystore
      secret:
        secretName: java-keystore
  volumeMounts:
    - name: tls-keystore
      mountPath: /var/tls
      readOnly: true
  jvmArgs:
    - "-Djavax.net.ssl.keyStore=/var/tls/keystore.jks"
    - "-Djavax.net.ssl.keyStorePassword=changeit"
----

Your application can now access:

* `/var/tls/keystore.jks`
* `/var/tls/keystore.password`

==== Example: Mount Configuration Files from a ConfigMap

.Create a ConfigMap with configuration files:

[source,bash]
----
kubectl create configmap app-configs \
  --from-file=log4j2.xml \
  --from-file=truststore.jks \
  -n my-apps
----
[start=2]
. Mount the files in your MuleApplication CR:
+
[source,yaml]
----
spec:
  volumes:
    - name: app-configs
      configMap:
        name: app-configs
  volumeMounts:
    - name: app-configs
      mountPath: /opt/mule/conf
      readOnly: true
----

==== Example: Use External Secret Manager (AWS Secrets Manager)

To integrate with AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault, use the Secrets Store CSI Driver.

[NOTE]
You must install the Secrets Store CSI Driver in your cluster. Refer to your cloud provider's documentation for installation instructions.

. Create a SecretProviderClass:
+
[source,yaml]
----
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: aws-database-secrets
  namespace: my-apps
spec:
  provider: aws
  parameters:
    objects: |
      - objectName: "production/database/credentials"
        objectType: "secretsmanager"
        jmesPath:
          - path: username
            objectAlias: db_username
          - path: password
            objectAlias: db_password
----
[start=2]
. Reference in MuleApplication CR:
+
[source,yaml]
----
spec:
  volumes:
    - name: aws-secrets
      csi:
        driver: secrets-store.csi.k8s.io
        readOnly: true
        volumeAttributes:
          secretProviderClass: aws-database-secrets
  volumeMounts:
    - name: aws-secrets
      mountPath: /mnt/secrets/aws
      readOnly: true
----
[start=3]
. Access Secrets:
+
The secrets are available at:

* `/mnt/secrets/aws/db_username`
* `/mnt/secrets/aws/db_password`

[start=4]
. Reference them in your Mule configuration:
+
[source,xml]
----
<db:config name="Database_Config">
  <db:my-sql-connection 
    host="${db.host}" 
    user="${file:/mnt/secrets/aws/db_username}" 
    password="${file:/mnt/secrets/aws/db_password}" />
</db:config>
----

==== Example: Use Azure Key Vault

To integrate with Azure Key Vault, configure a SecretProviderClass and reference it in your MuleApplication CR.

[source,yaml]
----
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: azure-key-vault-secrets
  namespace: my-apps
spec:
  provider: azure
  parameters:
    usePodIdentity: "false"
    useVMManagedIdentity: "true"
    userAssignedIdentityID: "<client-id>"
    keyvaultName: "my-keyvault"
    objects: |
      array:
        - |
          objectName: database-password
          objectType: secret
          objectVersion: ""
    tenantId: "<tenant-id>"
---
apiVersion: rtf.mulesoft.com/v1
kind: MuleApplication
metadata:
  name: my-app
spec:
  # ... other fields ...
  volumes:
    - name: azure-secrets
      csi:
        driver: secrets-store.csi.k8s.io
        readOnly: true
        volumeAttributes:
          secretProviderClass: azure-key-vault-secrets
  volumeMounts:
    - name: azure-secrets
      mountPath: /mnt/secrets/azure
      readOnly: true
----

==== Example: Mount a Persistent Volume

To mount a persistent volume for storing data that must survive pod restarts, use a PersistentVolumeClaim.

[source,yaml]
----
spec:
  volumes:
    - name: app-data
      persistentVolumeClaim:
        claimName: mule-app-pvc
  volumeMounts:
    - name: app-data
      mountPath: /mnt/data
----

Your application can read and write files to `/mnt/data`, and the data persists across pod restarts.

==== Example: Mount an Empty Directory (Temporary Storage)

To provide temporary storage that is created when a pod starts and deleted when it stops, use an emptyDir volume.

[source,yaml]
----
spec:
  volumes:
    - name: temp-storage
      emptyDir:
        sizeLimit: 1Gi
  volumeMounts:
    - name: temp-storage
      mountPath: /tmp/processing
----

=== Create a Connected App

Anypoint Controller requires a Connected App to authenticate with Anypoint Platform APIs. The Connected App acts on its own behalf using client credentials.

. Log in to Anypoint Platform.
. Navigate to *Access Management* > *Connected Apps*.
. Click *Create app*.
. Select *App acts on its own behalf (client credentials)*.
. Enter a name for your Connected App, such as `anypoint-controller`.
. Under *Scopes*, grant these permissions:
+
[%header%autowidth.spread]
|===
| Category | Permission | Description
| Exchange | Exchange Viewer | View and download application artifacts from Exchange
| General | View Environments | View environment details in the organization
| OpenID | Profile | Access basic profile information
| Runtime Manager | Create Applications | Create new application deployments
| Runtime Manager | Delete Applications | Delete existing application deployments
| Runtime Manager | Read Runtime Fabrics | View Runtime Fabric target information
|===

[start=7]
. Click *Save*.
. Copy the *Client ID* and *Client Secret*. You need these values in the next step.

[IMPORTANT]
Store the Client Secret securely. You cannot retrieve it again after leaving the create connected app page.


=== Configure Anypoint Credentials

Create a Kubernetes Secret `anypoint-credentials` containing the Connected App credentials in the namespace where Runtime Fabric is installed.

[source,bash]
----
kubectl create secret generic anypoint-credentials \
  --from-literal=ANYPOINT_CLIENT_ID=<your-client-id> \
  --from-literal=ANYPOINT_CLIENT_SECRET=<your-client-secret> \
  -n <rtf-namespace>
----

Replace the following:

* `<your-client-id>`: The Client ID from your Connected App
* `<your-client-secret>`: The Client Secret from your Connected App
* `<rtf-namespace>`: The namespace where Runtime Fabric is installed (for example, `rtf`)

Anypoint Controller monitors this secret and automatically reloads credentials when updated, enabling credential rotation without controller restarts.

==== Rotate Credentials

To rotate Connected App credentials:

. Create a new Connected App in Anypoint Platform or regenerate credentials.

. Update the secret:
+
[source,bash]
----
kubectl create secret generic anypoint-credentials \
  --from-literal=ANYPOINT_CLIENT_ID=<new-client-id> \
  --from-literal=ANYPOINT_CLIENT_SECRET=<new-client-secret> \
  -n <rtf-namespace> \
  --dry-run=client -o yaml | kubectl apply -f -
----

. The controller automatically detects the change and reloads credentials.

Follow these steps to deploy a Mule application using Anypoint Controller.

==== Create the Application Manifest

Create a file named `hello-world-app.yaml`:

[source,yaml]
----
apiVersion: rtf.mulesoft.com/v1
kind: MuleApplication
metadata:
  name: hello-world-app
  namespace: my-apps
spec:
  # Required: Anypoint Platform Configuration (Immutable)
  target: my-rtf-target
  businessGroup: MyOrg/Engineering
  environment: Production
  
  # Required: Runtime Configuration
  runtimeVersion: "4.8.0:2e-java8"
  
  # Required: Application Artifact
  application:
    group: my-org
    artifactId: hello-world
    version: "1.0.0"
    packaging: jar
  
  # Deployment Configuration
  replicas: 2
  resources:
    requests:
      cpu: 500m
      memory: 1Gi
    limits:
      cpu: 1000m
      memory: 2Gi
----

This example shows the minimum required fields. For a complete list of all available configuration fields, see xref:deploy-mule-app-anypoint-controller.adoc#understanding-custom-resource-definitions[Understanding Custom Resource Definitions].

==== Apply the Manifest

. Ensure the namespace exists:
+
[source,bash]
----
kubectl create namespace my-apps
----

. Apply the application manifest:
+
[source,bash]
----
kubectl apply -f hello-world-app.yaml
----

. Verify the Custom Resource was created:
+
[source,bash]
----
kubectl get muleapplication hello-world-app -n my-apps
----

When you apply the MuleApplication Custom Resource, Anypoint Controller perform these actions:

. Detects the new MuleApplication resource.
. Validates the configuration.
. Adds a label to the namespace for synchronization tracking.
. Creates the application in Anypoint Platform.
. Deploys the application to the specified Runtime Fabric target.
. Continuously monitors and reconciles the desired state.

==== Verify the Deployment

[source,bash]

=== Common Deployment Scenarios

[%collapsible]
.Common Deployment Scenarios
====
Customize your Mule application deployments for specific use cases.

*Deploy to a Specific Namespace*

You can deploy applications to any Kubernetes namespace:

[source,bash]
----
kubectl create namespace production-apps
kubectl apply -f my-app.yaml -n production-apps
----

The controller watches all namespaces and manages applications regardless of where the Custom Resource is created.

For more information about namespace permissions and flexibility, see xref:deploy-mule-app-anypoint-controller.adoc#understanding-runtime-fabric-agent-kubernetes-permissions[Understanding Runtime Fabric Agent Kubernetes Permissions].

*Deploy with Custom Logging*

Configure package-level logging for troubleshooting:

[source,yaml]
----
spec:
  scopeLoggingConfigurations:
    - scope: com.mulesoft
      logLevel: DEBUG
    - scope: org.mule.extension.http
      logLevel: INFO
    - scope: root
      logLevel: INFO
----

*Deploy with JVM Arguments*

Specify custom JVM arguments for memory tuning or SSL configuration:

[source,yaml]
----
spec:
  jvmArgs:
    - "-Xmx2048m"
    - "-Xms1024m"
    - "-Djavax.net.ssl.keyStore=/var/tls/keystore.jks"
----

*Deploy with Node Affinity*

Control which nodes run your application:

[source,yaml]
----
spec:
  pod:
    nodeSelector:
      environment: production
      disktype: ssd
    
    tolerations:
      - key: "dedicated"
        operator: "Equal"
        value: "mule-apps"
        effect: "NoSchedule"
----

For more Kubernetes customization options including affinity rules, topology spread constraints, and security context, see xref:deploy-mule-app-anypoint-controller.adoc#understanding-custom-resource-definitions[Understanding Custom Resource Definitions].

=== Status Conditions

The controller reports these status conditions:

[%collapsible]
.Status Condition: Applied
====
The `Applied` condition indicates whether the desired configuration was successfully synchronized with Anypoint Platform.

*Status: True (Success)*

[source,yaml]
----
status:
  conditions:
    - type: Applied
      status: "True"
      reason: APISuccessResponse
      message: "Configuration updated successfully"
      lastTransitionTime: "2024-01-15T10:30:00Z"
----

The controller successfully created or updated the application in Anypoint Platform. The application configuration matches the desired state defined in the CR.

*Status: False (Failure)*

[source,yaml]
----
status:
  conditions:
    - type: Applied
      status: "False"
      reason: APIErrorResponse
      message: "409 Conflict - Application name 'hello-world-app' already exists"
      lastTransitionTime: "2024-01-15T10:30:00Z"
----

The controller could not apply the configuration to Anypoint Platform. The `message` field contains the error details.

Common Failure Reasons:

* Application name already exists (not created via Anypoint Controller)
* Invalid Runtime Fabric target name
* Invalid business group or environment name
* Insufficient vCore entitlement
* Invalid runtime version
* Exchange artifact not found
* Connected App lacks required permissions
* Network connectivity issues to Anypoint Platform
====

[%collapsible]
.Status Condition: Available
====
The `Available` condition indicates whether the application has the desired number of ready replicas and is ready to serve traffic.

*Status: True (Available)*

[source,yaml]
----
status:
  readyReplicas: 2
  conditions:
    - type: Available
      status: "True"
      reason: HaveReadyReplicas
      message: "Application is ready to serve traffic"
      lastTransitionTime: "2024-01-15T10:32:00Z"
----

All desired replicas are running and ready. The application is serving traffic.

*Status: False (Not Available)*

[source,yaml]
----
status:
  readyReplicas: 0
  conditions:
    - type: Available
      status: "False"
      reason: HaveReadyReplicas
      message: "Application is not ready to serve traffic"
      lastTransitionTime: "2024-01-15T10:32:00Z"
----

The application doesn't have ready replicas. Check pod status and logs to diagnose the issue.
====

[%collapsible]
.Status Condition: DesiredSpecAppliedOnCluster
====
The `DesiredSpecAppliedOnCluster` condition indicates whether the currently deployed application version in the cluster matches the desired specification version in Anypoint Platform.

*Status: True (Synchronized)*

[source,yaml]
----
status:
  anypointVersion: v789
  conditions:
    - type: DesiredSpecAppliedOnCluster
      status: "True"
      reason: DesiredSpecAppliedOnCluster
      lastTransitionTime: "2024-01-15T10:33:00Z"
----

The running application version matches the desired version. Deployment is complete and synchronized.

*Status: False (Out of Sync)*

[source,yaml]
----
status:
  conditions:
    - type: DesiredSpecAppliedOnCluster
      status: "False"
      reason: DesiredSpecAppliedOnCluster
      lastTransitionTime: "2024-01-15T10:33:00Z"
----

The cluster is still deploying the updated version, or the deployment is in progress.
====

== Manage Mule Applications

Anypoint Controller enables you to manage the complete lifecycle of your Mule applications using standard Kubernetes commands and GitOps workflows.

=== Reconciliation Behavior

Anypoint Controller continuously reconciles the desired state:

* The controller synchronizes the application state every 30 seconds.
* The controller compares the CR spec hash with the last published hash to detect changes.
* When changes are detected, the controller updates Anypoint Platform automatically.
* Failed operations are retried with exponential backoff.
* The controller periodically refreshes state even without changes (every 10 minutes).

Manage your application lifecycle:

* <<update-a-mule-application,Update a Mule Application>>
* <<delete-a-muleapplication,Delete a MuleApplication>>
* <<pause-reconciliation,Pause Reconciliation>>

=== Update a Mule Application

. Modify your Mule application YAML file:

[source,yaml]
----
spec:
  replicas: 5  # Changed from 2 to 5
----
[start=2]
. Apply the change:

[source,bash]
----
kubectl apply -f hello-world-app.yaml
----
[start=3]
. Monitor the update:

[source,bash]
----
kubectl get muleapplication hello-world-app -n my-apps -w
----

The controller detects the change and initiates the update automatically.

[NOTE]
Some fields like `target`, `businessGroup`, and `environment` are immutable and cannot be changed after creation. For a complete list of mutable and immutable fields, see xref:deploy-mule-app-anypoint-controller.adoc#understanding-custom-resource-definitions[Understanding Custom Resource Definitions].

=== Delete a MuleApplication

To delete an application managed by Anypoint Controller, delete the MuleApplication CR:

[source,bash]
----
kubectl delete muleapplication <app-name> -n <namespace>
----

Example:

[source,bash]
----
kubectl delete muleapplication hello-world-app -n my-apps
----

The controller automatically:

. Deletes the application from Anypoint Platform.
. Removes all Kubernetes resources (Deployment, Service, ConfigMaps, Secrets).
. Removes the finalizer from the CR.
. Allows Kubernetes to delete the CR.

[IMPORTANT]
Deletion is permanent. Ensure your Git repository contains the application configuration if you need to redeploy later.


=== Pause Reconciliation

To temporarily prevent the controller from updating an application, add an annotation:

[source,bash]
----
kubectl annotate muleapplication hello-world-app \
  rtf.mulesoft.com/reconcile=false \
  -n my-apps
----

To resume:

[source,bash]
----
kubectl annotate muleapplication hello-world-app \
  rtf.mulesoft.com/reconcile- \
  -n my-apps
----

== Understanding Runtime Fabric Agent Kubernetes Permissions

The Runtime Fabric agent requires specific Kubernetes permissions to manage MuleApplication Custom Resources:

* Namespace Editing +
The Runtime Fabric agent needs permissions to edit the Kubernetes namespace where you deploy the MuleApplication CR to add synchronization labels required for tracking and reconciliation.

* Namespace Flexibility +
You can create MuleApplication Custom Resources in any Kubernetes namespace. The controller watches all namespaces and manages applications regardless of where the CR is created.

* Resource Creation +
The controller creates application resources (Deployments, Services, ConfigMaps, Secrets) in the same namespace as the MuleApplication CR.

* Label Management +
The controller adds labels to resources for tracking, ownership, and reconciliation purposes.

[%collapsible]
.Required Fields (Immutable After Creation)
====
These fields are required and can't be changed after the application is created:

* `target` (string): The name of the Runtime Fabric target as shown in Runtime Manager.
+
[source,yaml]

spec:
  target: production-rtf
----

* `businessGroup` (string): The hierarchical path of the Anypoint business group. Use forward slashes to separate parent and child groups.
+
[source,yaml]
----
spec:
  businessGroup: Acme/Finance/MyGroup
----
+
If your business group is the root organization, use only the organization name:
+
[source,yaml]
----
spec:
  businessGroup: Acme
----

* `environment` (string): The name of the Anypoint environment (not the environment ID).
+
[source,yaml]
----
spec:
  environment: Production
----

[%collapsible]
.Required: Runtime Version
====
The `runtimeVersion` (string) specifies the Mule runtime version to use. Must be version 4.6 or above.

[source,yaml]

spec:
  runtimeVersion: "4.8.0:2e-java8"

[%collapsible]
.Required: Application Artifact
====
The `application` field specifies the artifact to deploy from Anypoint Exchange, using Maven coordinate conventions:

[source,yaml]

spec:

    group: my-business-group      # Business group that owns the artifact

    packaging: jar                 # Artifact format (typically "jar")

[%collapsible]
.Deployment Configuration
====
*Replicas*

The `replicas` field specifies the number of application instances:

[source,yaml]
----
spec:
  replicas: 3
----

* Default: `1`
* Maximum: `16` replicas per application

*Resource Allocation*

The `resources` field defines CPU and memory resources per replica:

[source,yaml]
----
spec:
  resources:
    requests:
      cpu: 500m        # Minimum CPU (millicores)
      memory: 1Gi      # Minimum memory
    limits:
      cpu: 2000m       # Maximum CPU
      memory: 2Gi      # Maximum memory
----

*Update Strategy*

The `updateStrategy` field controls how updates are rolled out:

[source,yaml]
----
spec:
  updateStrategy: rolling  # or "recreate"
----

* `rolling` (default): Updates replicas incrementally, maintaining availability
* `recreate`: Terminates all replicas before creating new ones

*Horizontal Pod Autoscaling*

The `autoscaling` field configures CPU-based autoscaling:

[source,yaml]
----
spec:
  autoscaling:
    enabled: true
    minReplicas: 2
    maxReplicas: 10
----

When autoscaling is enabled, the controller creates a HorizontalPodAutoscaler resource that automatically adjusts replica count based on CPU utilization.

*Clustering and Persistence*

Configure Mule clustering for high availability and enable persistent object store for stateful applications.

[source,yaml]
----
spec:
  clustered: true                  # Enable Mule clustering
  persistentObjectStore: true      # Enable persistent object store
----

*Replica Distribution*

When enabled, Kubernetes ensures replicas are distributed across different nodes for high availability.

[source,yaml]
----
spec:
  enforceDeployingReplicasAcrossNodes: true
----

=== Mounting Properties from External Sources

The `propertiesFrom` field in the MuleApplication CR `spec` enables you to inject application properties from Kubernetes Secrets and ConfigMaps without hardcoding them in the Custom Resource.

[source,yaml]
----
spec:
  propertiesFrom:
    - secretRef:
        name: my-secret
    - configMapRef:
        name: my-config
----

When you reference a Secret or ConfigMap in `propertiesFrom`, the controller:

. Creates `volume` and `volumeMount` configurations automatically.
. Mounts the files to `/etc/mule/properties/` in the Mule application container.
. The Mule agent scans this directory recursively and loads properties before starting the application.

==== Supported Property Formats

The Mule agent supports two property file formats:

* Java Properties Files (`.properties` extension):
** Files ending with `.properties` are parsed as standard Java properties files
** Each line follows the `key=value` format
** Supports comments with `#` or `!`

* File-as-Property (any other file):
** The filename becomes the property name
** The file content becomes the property value
** Useful for single-value secrets

Properties are loaded alphabetically by source name. Later properties override earlier ones with the same name.

[%collapsible]
.Example: Mount Properties from a Secret
====
. Create a Secret:
+
[source,bash]
----
kubectl create secret generic database-credentials \
  --from-literal=db.username=admin \
  --from-literal=db.password=secretPass123 \
  --from-literal=db.host=database.example.com \
  -n my-apps
----

. Reference it in your MuleApplication:
+
[source,yaml]
----
spec:
  propertiesFrom:
    - secretRef:
        name: database-credentials
----

. Access properties in your Mule application:
+
[source,xml]
----
<db:config name="Database_Config">
  <db:my-sql-connection 
    host="${db.host}" 
    user="${db.username}" 
    password="${db.password}" />
</db:config>
----
====

[%collapsible]
.Example: Mount Properties from a ConfigMap
====

. Create a ConfigMap:
+
[source,bash]
----
kubectl create configmap app-config \
  --from-literal=api.timeout=30000 \
  --from-literal=api.retry.count=3 \
  --from-literal=api.base.url=https://api.example.com \
  -n my-apps
----

. Reference it in your MuleApplication:
+
[source,yaml]
----
spec:
  propertiesFrom:
    - configMapRef:
        name: app-config
----
====

[%collapsible]
.Example: Mount a Java Properties File
====

. Create a properties file:
+
[source,properties]
----
# application.properties
http.port=8081
http.host=0.0.0.0
api.key=prod-key-12345
max.retry.attempts=5
timeout.seconds=30
----

. Create a ConfigMap from the file:
+
[source,bash]
----
kubectl create configmap app-properties \
  --from-file=application.properties \
  -n my-apps
----

. Reference it in your MuleApplication:
+
[source,yaml]
----
spec:
  propertiesFrom:
    - configMapRef:
        name: app-properties
----
+
All properties from the file are loaded and available as `${http.port}`, `${api.key}`, etc.
====

[%collapsible]
.Example: Combine Multiple Property Sources
====
To combine properties from multiple Secrets and ConfigMaps, list them in the order they should be loaded, where later sources override earlier ones if property names conflict.

[source,yaml]
----
spec:
  propertiesFrom:
    - secretRef:
        name: database-credentials    # Loaded first
    - configMapRef:
        name: app-config              # Loaded second (overrides conflicts)
    - secretRef:
        name: api-keys                # Loaded third (overrides conflicts)
----
====

[%collapsible]
.Example: Optional Property Sources
====
Make a property source optional (doesn't fail if not found):

[source,yaml]
----
spec:
  propertiesFrom:
    - configMapRef:
        name: optional-config
        optional: true    # Don't fail if this ConfigMap doesn't exist
----
====

=== Template Restrictions

When using Anypoint Controller, certain Runtime Fabric templates are not supported.

[%header%autowidth.spread]
|===
| Template | Support Status | Alternative
| KubernetesTemplate | Not supported | Define all Kubernetes-specific configurations directly in the MuleApplication Custom Resource fields (`spec.pod`, `spec.service`, `spec.deployment`)
| HttpRouteTemplate | Not supported | Manage HTTP routing and ingress configurations separately using standard Kubernetes Ingress resources or your cluster's ingress controller
| Ingress Template | Not supported | Manage ingress configurations separately using standard Kubernetes Ingress resources or your cluster's ingress controller
|===

Templates were designed for imperative application management through Runtime Manager. With Anypoint Controller's declarative GitOps approach, all configuration must be explicitly defined in the Custom Resource to maintain:

* A single source of truth in version control
* Complete visibility of application configuration
* Reproducible deployments across environments

==== Migrating from Templates

If you currently use KubernetesTemplate for configuration, migrate those settings to the MuleApplication CR fields:

[%header%autowidth.spread]
|===
| Template Field | MuleApplication CR Field
| Pod labels | `spec.pod.metadata.labels`
| Pod annotations | `spec.pod.metadata.annotations`
| Node selectors | `spec.pod.nodeSelector`
| Tolerations | `spec.pod.tolerations`
| Affinity rules | `spec.pod.affinity`
| Topology spread | `spec.pod.topologySpreadConstraints`
| Service annotations | `spec.service.metadata.annotations`
| Deployment labels | `spec.deployment.metadata.labels`
|===

== Troubleshooting

Use these techniques to diagnose and resolve common issues with Anypoint Controller and Mule application deployments.

=== Check Controller Logs

View Anypoint Controller logs:

[source,bash]
----
kubectl logs -l app=rtf-agent -n <rtf-namespace> -c anypoint-controller --tail=100
----

Follow logs in real-time:

[source,bash]
----
kubectl logs -l app=rtf-agent -n <rtf-namespace> -c anypoint-controller -f
----

=== Common Issues

[%collapsible]
.Application Not Reconciling
====
The `Applied` condition remains `False` or changes aren't reflected.

To resolve this issue:

. Verify the namespace has the correct label:
+
[source,bash]
----
kubectl get namespace <namespace> --show-labels
----
+
The namespace should have `rtf.mulesoft.com/system-ns=<rtf-namespace>`.
+
Add the label if missing:
+
[source,bash]
----
kubectl label namespace <namespace> rtf.mulesoft.com/system-ns=<rtf-namespace>
----

. Check the Connected App credentials:
+
[source,bash]
----
kubectl get secret anypoint-credentials -n <rtf-namespace> -o yaml
----

. Verify the Connected App has required permissions in Anypoint Platform.
. Check controller logs for errors.
====

[%collapsible]
.Application Deployment Fails
====

The `Applied` condition is `True`, but `Available` is `False`.

To resolve this issue:

. Check pod status:
+
[source,bash]
----
kubectl get pods -n <namespace> -l rtf.mulesoft.com/app=<app-name>
----

. View pod logs:
+
[source,bash]
----
kubectl logs <pod-name> -n <namespace>
----

. Check pod events:
+
[source,bash]
----
kubectl describe pod <pod-name> -n <namespace>
----

. Common causes:
   - Invalid runtime version
   - Artifact not found in Exchange
   - Insufficient resources (CPU/memory)
   - Image pull errors
====

[%collapsible]
.Invalid Configuration
====

`kubectl apply` fails with validation errors.

To resolve this issue:

. Validate the YAML syntax:
+
[source,bash]
----
kubectl apply -f app.yaml --dry-run=server
----

. Check immutable field violations (target, businessGroup, environment cannot be changed after creation).

. Verify required fields are present.
====

[%collapsible]
.Anypoint Platform API Errors
====
The `Applied` condition shows `APIErrorResponse`.

To resolve this issue:

. Read the error message in the status condition.
+
 Common errors:
   - `409 Conflict`: Application name already exists (created outside Anypoint Controller)
   - `404 Not Found`: Invalid target, business group, or environment name
   - `403 Forbidden`: Connected App lacks permissions
   - `400 Bad Request`: Invalid configuration (for example, runtime version)

. Verify configuration matches your Anypoint Platform setup.
====
