= Configuring Ingress with HTTP Route-Template Custom Resource in Runtime Fabric

Configure ingress support for Mule apps on the Anypoint Runtime Fabric platform using the HTTP route-template custom resource.

== Benefits of Ingress Configuration with the HTTP Route-Template Custom Resource

Current ingress support for Mule apps on the Runtime Fabric platform is confined to https://kubernetes.io/docs/concepts/services-networking/ingress/[Kubernetes ingress] resources, which restrict you from using cloud vendor-native HTTP routing solutions, such as OpenShift Routes on OpenShift clusters, Istio, or Service Mesh. To address this limitation, Runtime Fabric supports a custom resource `httproutetemplates.rtf.mulesoft.com` template.

Use the HTTP route-template custom resource in Runtime Fabric to define and implement custom routing configurations. With this approach, you can take advantage of compatibility with a range of ingress controllers and cloud-native routing mechanisms, including support for:

* Wildcard for host-based routing
* Creation of `httproutetemplates.rtf.mulesoft.com` templates to map a set of application endpoints to arbitrary HTTP routing resources for path-based routing
* Synchronization of domains or hosts from the HTTP route templates with the Anypoint control plane
* Using parameter placeholders in `httproutetemplates.rtf.mulesoft.com` templates for additional extensibility

== HTTP Route-Template Custom-Resource Placeholders

Runtime Fabric provides placeholder properties that cluster administrators can use in their HTTP route-template custom resource. These placeholders are evaluated and replaced with actual data by Runtime Fabric when rendering the deployment charts.

As a cluster administrator, use these HTTP route-template placeholder properties in your CRD (custom resource definition):

[%header%autowidth.spread]
|===
| Property| Description
| `{{ .ResourceName }}`| Runtime Fabric generated unique routing
| `{{ .ApplicationName }}`| Mule app deployment name
| `{{ .Namespace }}`| Namespace of the Mule app deployment
| `{{ .Service.Name }}`| Backend service name of the Mule app deployment
| `{{ .Service.PortName }}`| Backend service port name of the Mule app deployment
| `{{ .Service.Port }}`| Backend service port number of the Mule app deployment
| `{{ .Host }}`| Host or domain value from the public endpoint of Mule  app deployment
| `{{ .Path }}`| Path value from the public endpoint of Mule app deployment
| `{{ .OrganizationID }}`| Organization ID of the Mule app deployment
| `{{ .EnvironmentID }}`| Environment ID of the Mule app deployment
| `{{ .UniqueId }}`| Unique ID.
|===

== How the HTTP Route-Template Custom Resource Works in Runtime Fabric

This diagram provides an overview of how to configure ingress using an HTTP route-template custom resource in Runtime Fabric:

image::ingress-http-diagram.png[HTTP route-template diagram overview]

The `httproutetemplates` resource applies only to new Mule app deployments created after the template resource is set up. It doesn't affect existing deployments. If you redeploy a Mule app after creating or updating the `httproutetemplates`, the new template is applied.

The `httproutetemplates` resource enables you to configure routes like these:

* `baseEndpoints` 
+
Endpoints associated with the routing resources defined in the template. These endpoints are synchronized by Runtime Fabric with the Anypoint control plane. Application developers can select from a list of synchronized base endpoints during deployment and optionally customize the path and subdomain when applicable.

* `resources` +
Kubernetes routing resource templates, which are created for every matching Mule app ingress endpoint.

To get the CRD of key elements available to configure for the template, retrieve the Kubernetes specification by running this command:

----
kubectl get crd httproutetemplates.rtf.mulesoft.com -o yaml
----

== HTTP Route-Template Examples

Review these HTTP route-templates examples for Kubernetes ingress, OpenShift routes, and Kubernetes Gateway API (HTTPRoute).


=== Example for Kubernetes Ingress
This example shows an HTTP route-template resource for Kubernetes ingress:

----
apiVersion: rtf.mulesoft.com/v1
kind: HTTPRouteTemplate
metadata:
  name: test-template-ingress
  namespace: rtf
spec:
  baseEndpoints:
    - https://*.example.com
    - https://example.internal.com
  resources:
    - |
      apiVersion: networking.k8s.io/v1
      kind: Ingress
      metadata:
        name: {{ .ResourceName }}
        namespace: {{ .Namespace }}
        labels:
        annotations:
      spec:
       ingressClassName: nginx 
       tls:
       - hosts:
         - {{ .Host }}
         secretName: testsecret-tls
       rules:
       - host: {{ .Host }} 
         http:
            paths: 
            - pathType: Prefix
              path: {{ .Path }}
              backend: 
                service:
                  name: {{ .Service.Name }}
                  port:
                    name: {{ .Service.PortName }}
----

[calloutlist]

.. Hosts or domains used for mapping the public endpoints configured on the Mule app deployment.
.. One or more Kubernetes routing resources, such as an Ingress resource.
.. The Runtime Fabric-generated unique routing resource name. Use this placeholder to make sure the Kubernetes resource name meets the uniqueness constraint. If you don’t use this placeholder, make sure the resource name is unique.
.. Host or domain from the Mule app's public URL.
.. Path from the Mule app's public URL. 


=== Example for OpenShift Routes
This example shows an HTTP route-template resource for OpenShift routes:

----
apiVersion: rtf.mulesoft.com/v1
kind: HTTPRouteTemplate
metadata:
  name: test-template-routes
  namespace: rtf
spec:
  baseEndpoints:
    - https://demo.example.com
  resources:
    - |
apiVersion: v1
kind: Route
metadata:
  name: {{ .ResourceName }}
  namespace: {{ .Namespace }}
spec:
  host: {{ .Host }}
  path: {{ .Path }}
  to:
    kind: Service
    name: {{ .Service.Name }}
  tls:
    termination: edge
    key: |-
      -----BEGIN PRIVATE KEY-----
      [...]
      -----END PRIVATE KEY-----
    certificate: |-              
      -----BEGIN CERTIFICATE-----
      [...]
      -----END CERTIFICATE-----
    caCertificate: |-
      -----BEGIN CERTIFICATE-----
      [...]
      -----END CERTIFICATE-----

----

=== Example for Kubernetes Gateway API

This example shows an HTTP route-template resource for Kubernetes Gateway API (HTTPRoute):

----
apiVersion: rtf.mulesoft.com/v1
kind: HttpRouteTemplate
metadata:
  name: k8s-gateway-api-cr
  namespace: rtf
spec:
  baseEndpoints:
    - https://demo.example.com
  resources: |-
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: {{ .ResourceName }}
  namespace: {{ .Namespace }}
spec:
  parentRefs:
  - kind: Gateway
    name: cluster-gateway
  hostnames:
  - {{ .Host }}
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: {{ .Path }}
    backendRefs:
    - name: {{ .Service.Name }}
      port: {{ .Service.Port }}

----

[NOTE]
You are responsible for the configuration of the Kuberneates Gateway resources and allowing HTTP Routes from the route's namespace to be attached.


== Using TLS in the HTTP Route-Template Custom Resource

To use TLS in the routing resources in an HTTP route template, create a TLS secret in the Runtime Fabric namespace. For details, refer to the https://kubernetes.io/docs/concepts/services-networking/ingress/#tls[Kubernetes TLS] documentation.

To configure the Runtime Fabric to manage the secrets lifecycle (Create, Update, and Delete) across all application namespace, use the `rtf.mulesoft.com/synchronized: "true"` label on the TLS secret. For example:

----
apiVersion: v1
kind: Secret
metadata:
  name: testsecret-tls
  namespace: <agent-namespace>
  labels:
    rtf.mulesoft.com/synchronized: "true"
data:
  tls.crt: base64 encoded cert
  tls.key: base64 encoded key
type: kubernetes.io/tls

----

Using this label is highly recommended for secrets management. If you don’t add this label, you must manually update the secret in each namespace.

== Modify an Existing HTTP Route-Template CRD

You can modify existing `httproutetemplates` templates even if they are used for application deployments. Note that previously created HTTP routing resources based on this template aren’t updated if you modify the template.

To update existing HTTP routing resources with the template changes, perform a redeployment of the Mule app from the Anypoint control plane. For example, if you update the base domain, which requires changing the endpoint for the ingress template, remove the old endpoint and add the new one as part of the application redeployment.
